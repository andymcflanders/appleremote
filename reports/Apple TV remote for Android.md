# Companion Link Carries Almost the Whole Remote

An Android phone can do nearly everything Apple's own iPhone remote does, and **one PIN pairing over Apple's undocumented Companion Link protocol covers most of it**. That one pairing gives the D-pad and every Siri Remote button except voice, a touchpad that streams gestures at about 60 Hz, a real keyboard that opens by itself when a tvOS text field gets focus, and the installed-app list with direct launch and deep links. It also gives sleep/wake with power-state tracking, relative volume (absolute volume too when audio goes to a HomePod), and switching between user profiles. **A second, independent PIN pairing over AirPlay 2** adds the full now-playing screen: title, artwork, position, seek, and shuffle/repeat, plus audio-output selection. AirPlay 2 has carried the older MRP protocol inside a special stream since tvOS 15. Siri voice is unproven and the sources disagree on it. App icons from the device, the true foreground app, restart and notifications have no known message at all. Apple publishes no control API, so every implementation comes from the reverse-engineered pyatv library, whose 0.18.0 release from June 2026 is still the newest. Small, unannounced handshake changes have broken third-party clients at tvOS 15, 18.4 and 26.5, and again in tvOS 27 (shipped September 14, 2026), where AirPlay pairing can fail to show a PIN at all. The good news for a builder is that this is no longer a research project. At least six open-source native-Kotlin Android remotes appeared in 2026. One of them, msthind04/AppleTV-Remote (Apache-2.0), already has a pure-JVM protocol module for both protocols, tested byte-for-byte against pyatv. The recommended route is a native Kotlin app built on that module and checked against pyatv master. Ship the two Companion-only tiers first, treat the AirPlay tier as the high-risk add-on it currently is, and keep a standing budget for tvOS regressions.

## Two undocumented protocols and two PINs stand in for an API

**There is no official way in.** As one Android implementer puts it, "Apple publishes no API for controlling an Apple TV", and since tvOS 15 the only route is Companion Link ([msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote)). The only piece Apple documents is the HomeKit Accessory Protocol (HAP) specification, whose pairing and encryption these protocols borrow ([Apple HomeKit specification](https://developer.apple.com/homekit/specification/); [pyatv Protocols](https://pyatv.dev/documentation/protocols/)). Apple's Android "Apple TV" app gained Google Cast output, not remote control ([Croma Unboxed](https://www.croma.com/unboxed/apple-tv-android-google-cast-support)).

Regulation will not change this soon. The EU's March 2025 DMA interoperability decisions cover **iOS** connectivity features for connected devices. They do not require tvOS to accept third-party controllers ([European Commission](https://digital-markets-act.ec.europa.eu/commission-provides-guidance-under-digital-markets-act-facilitate-development-innovative-products-2025-03-19_en)). As of March 2026, none of the 56 formal interoperability requests Apple received had produced a working solution ([FSFE](https://fsfe.org/news/2026/news-20260420-01.en.html)). Matter's Casting Video Player device type would offer an official key-press and content-launch interface, and Amazon implements it on Fire TV. There is no evidence that tvOS supports it ([Amazon Developer](https://developer.amazon.com/docs/fire-tv/overview-of-matter-casting.html); [Trusted Reviews](https://www.trustedreviews.com/news/matter-tv-casting-tech-could-replace-airplay-and-google-cast-4190428)). Reverse engineering will remain the only path for the life of a first app version.

**Companion Link (`_companion-link._tcp`) does most of the work.** Apple moved the iOS Control Center remote widget from MRP to Companion in iOS 13 ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). Today Companion carries HID buttons and touch gestures, text input, app listing and launching, user accounts, power and attention state, and coarse media-capability flags. Each frame starts with a 1-byte type and a 3-byte big-endian length. After pair-verify, each payload is an OPACK dictionary with four fields: `_i` (message name), `_t` (event, request or response), `_x` (transaction ID) and `_c` (content). The payload is encrypted with ChaCha20-Poly1305, using a 12-byte little-endian counter nonce per direction and the frame header as AAD (same source). OPACK is Apple's compact CoreUtils serialization format and is only partly documented. pyatv warns that its table is "not complete or verified to be correct" (same source). Where pyatv's prose and code disagree, follow the code. Its docs mislabel some pairing frames and OPACK rows, and its MRP and AirPlay pages mostly date from 2021.

**MRP, the older protocol behind now-playing data, now exists only inside AirPlay 2.** In September 2021, tvOS 15 removed the standalone `_mediaremotetv._tcp` service. In pyatv's words, "in practice they didn't get rid of it, they just allocated a special stream type in AirPlay (2) and decided to tunnel MRP over it" ([pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). Reaching MRP takes an RTSP exchange on port 7000: a `SETUP` with `isRemoteControlOnly` that returns an event port, then `RECORD`, then a `200 OK` reply to the receiver's `POST /command` (without it the Apple TV closes the connection after 30 seconds), then a second `SETUP` for stream type 130 that returns a data port, and finally a `POST /feedback` heartbeat every two seconds for as long as the session lives ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). On the data channel, each message has a 32-byte `sync`/`rply` header, then a binary plist, then varint-prefixed protobuf messages. pyatv itself calls this format "mostly educated guesses" (same source). **A full-featured client therefore keeps four encrypted TCP connections open at once:** Companion, AirPlay control, event and data.

**Both protocols pair the same way; only the envelope differs.** Pair-setup uses SRP-6a over the RFC 5054 3072-bit group with SHA-512. The username is `Pair-Setup` and the password is the four-digit PIN shown on the TV. Long-term identities are Ed25519 keys. Pair-verify uses ephemeral X25519 keys with Ed25519 signatures. Session keys come from HKDF-SHA512 with protocol-specific strings ([pyatv hap_srp.py](https://github.com/postlund/pyatv/blob/master/pyatv/auth/hap_srp.py)). Apple scopes each pairing to one service. pyatv's wizard pairs Companion first, then "continues to AirPlay pairing and waits for another PIN" ([pyatv #2866](https://github.com/postlund/pyatv/issues/2866)). AirPlay also has a PIN-free "transient" pairing (fixed PIN 3939, steps M1–M4 only). It works for HomePods but not for the Apple TV's MRP tunnel. pyatv opens that tunnel only with full HAP credentials, and only on devices whose model starts with `AppleTV` ([pyatv airplay/utils.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/airplay/utils.py); [pyatv hap_transient.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/airplay/auth/hap_transient.py)).

| | Companion Link | AirPlay 2 remote-control stream (MRP tunnel) |
|---|---|---|
| Discovery | `_companion-link._tcp`; advertised port rotates | `_airplay._tcp`; usually port 7000 |
| Pairing transport | OPACK `_pd` inside `PS_Start`/`PS_Next` and `PV_Start`/`PV_Next` frames | HTTP `POST /pair-pin-start`, `/pair-setup`, `/pair-verify` with `X-Apple-HKP: 3` |
| HKDF-SHA512 session keys (salt / info) | empty / `ClientEncrypt-main`, `ServerEncrypt-main` | `Control-Salt` / `Control-Write-` and `Control-Read-Encryption-Key`; `Events-*`; `DataStream-Salt<seed>` / `DataStream-Output-` and `-Input-Encryption-Key` |
| Framing after verify | 4-byte header plus ChaCha20-Poly1305-sealed OPACK | `[2-byte LE length][ciphertext][16-byte tag]` blocks; data channel adds 32-byte header, binary plist, varint protobufs |
| Delivers | buttons, touch, keyboard, apps, accounts, power, media flags, volume | metadata, artwork, position, seek, shuffle/repeat, per-output volume, output selection |
| tvOS setting that gates pairing | Settings > Remotes and Devices > Remote App and Devices | AirPlay "Allow Access" set to Anyone on the Same Network (Home app: Speakers & TV, Allow Everyone) |

Sources: [pyatv Protocols](https://pyatv.dev/documentation/protocols/); [companion/protocol.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/protocol.py); [airplay/auth/hap.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/airplay/auth/hap.py); [HA core #173352](https://github.com/home-assistant/core/issues/173352); [pyatv troubleshooting](https://pyatv.dev/support/troubleshooting/); [pyatv #2908](https://github.com/postlund/pyatv/issues/2908).

pyatv stores credentials per protocol as `hex(ltpk):hex(ltsk):hex(atv_id):hex(client_id)` ([pyatv hap_pairing.py](https://github.com/postlund/pyatv/blob/master/pyatv/auth/hap_pairing.py)). This suggests a client can reuse one Ed25519 identity for both pairings and keep a separate device key and ID per protocol. That is an inference: no source confirms whether one protocol's credentials are rejected by the other.

The reference implementation also cuts a security corner. pyatv's pair-setup code has a `# TODO: verify signature here` where it should check the Apple TV's M6 signature ([pyatv hap_srp.py](https://github.com/postlund/pyatv/blob/master/pyatv/auth/hap_srp.py)). A Rust port's audit says pyatv also skips verifying the accessory's SRP proof and the pair-verify M2 signature ([rust-atv](https://github.com/PapeThePope/rust-atv)). These checks stop a spoofed device on the LAN from impersonating the TV, so an Android port should perform all three.

**Discovery is plain mDNS, but unreliable.** The AirPlay TXT record gives a stable `deviceid`, `model`, `osvers` and a 64-bit `features` mask, while in the Companion record only `rpMd`, `rpFl` and `rpVr` are stable and the other values rotate ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). `rpFl & 0x4000` signals PIN-pairing support, which screens out the HomePods, Macs and iPads that also advertise Companion but cannot be paired ([pyatv companion/__init__.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/__init__.py)). A Bonjour Sleep Proxy may advertise a sleeping Apple TV with every port set to 0, and opening a TCP connection to one of those ports wakes it ([pyatv scan.py](https://github.com/postlund/pyatv/blob/master/pyatv/core/scan.py); [pyatv knock.py](https://github.com/postlund/pyatv/blob/master/pyatv/support/knock.py)). Multicast fails often enough in 2026 reports, behind mDNS reflectors and across routed subnets, that a manual-IP path with unicast mDNS queries is mandatory ([pyatv #2944](https://github.com/postlund/pyatv/issues/2944); [HA core #184270](https://github.com/home-assistant/core/issues/184270)). Worse, the Apple TV "rotates the ephemeral port it advertises for Companion Link, even while it is awake and playing", which kills open connections; the fix is to key credentials on a stable identifier and rediscover over mDNS before every reconnect ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)). msthind04 keys on Companion's `rpMRtID`, while pyatv matches devices through identifiers from the other services ([pyatv concepts](https://pyatv.dev/documentation/concepts/)), and either works as long as the key never includes host or port.

**The legal exposure is modest but real.** US law (DMCA §1201(f)) and EU law (Software Directive Arts. 5(3) and 6, which Art. 9(1) protects from contractual override) have interoperability carve-outs. They cover building an independent client from observed behavior ([Perzanowski, UC Davis L. Rev.](https://www.perzanow.ski/s/UC-DavisLR-Interop.pdf)). The protocols need no Apple-signed keys and no DRM circumvention: pairing is PIN-based, and the response to the `/auth-setup` step can be ignored ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). Home Assistant has shipped this kind of control publicly for years ([HA Apple TV integration](https://www.home-assistant.io/integrations/apple_tv/)). The practical risk is trademark. The app should not be called "Apple TV Remote" and should not imply Apple's endorsement. This is not legal advice.

### Buttons and touchpad ride fire-and-forget events

Every Siri Remote button except voice maps to a Companion `_hidC` request. The request carries a button code and `_hBtS` (1 = pressed, 2 = released). The codes are 1–4 for the D-pad, 5 Menu, 6 Select, 7 Home, 8/9 volume, 10 Siri, 11 Screensaver, 12 Sleep, 13 Wake, 14 Play/Pause, 15/16 Channel, 17 Guide and 18/19 Page Up/Down ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). Double-press and long-press are only timing. For a double tap pyatv sends two down/up pairs back to back. For a long press it holds the button down for one second ([companion/__init__.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/__init__.py)).

Media keys have a second path through `_mcc`. It covers play, pause, next, previous, skip by a float number of seconds in `_skpS`, and the begin/end messages for fast-forward and rewind. The `_iMC` event's `_mcF` bitmask tells the client which of these the current app accepts ([companion/api.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/api.py); [pyatv protocols.md](https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md)). Apps still decide which playback commands they honor, so a button that does nothing in one app may work in another ([HA apple_tv doc](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/apple_tv.markdown)).

Two button details are unsettled. **Codes 18 and 19 mean different things in different sources.** pyatv names them Page Up and Page Down and, since 0.17.0 (January 2026), sends 19 as its dedicated Control Center command ([PR #2699](https://github.com/postlund/pyatv/pull/2699); [companion/__init__.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/__init__.py)), whereas a January 2024 capture of Apple's iOS 17.3 Remote labels 18 as mute and 19 as power ([pyatv #2325](https://github.com/postlund/pyatv/issues/2325)). Both readings may be right in different contexts, so the app should test them on tvOS 26 and tvOS 27 hardware before labeling the buttons. For Control Center, code 19 is still a better bet than a timed Home hold, which a long-open issue reports acting like a plain Home press ([pyatv #2286](https://github.com/postlund/pyatv/issues/2286)). **The app switcher has no dedicated code** and no public confirmation on tvOS 26/27, although dvdsgl's remote lists an app switcher among its features ([dvdsgl/tv-remote](https://github.com/dvdsgl/tv-remote)).

The touchpad works the same way and costs as little. The client registers a virtual 1000 × 1000 surface with `_touchStart`, then streams `_hidT` events, each carrying a phase `_tPh` (1 press, 3 move, 4 release), coordinates `_cx`/`_cy` and a nanosecond timestamp; pyatv sends one every **16 ms** ([companion/api.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/api.py); [pyatv protocols.md](https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md)). A click is `_hidC` 6 down and up followed by a phase-5 event at (1000, 1000), and a drag that reaches the edge of the surface must be released and pressed again, or the cursor moves backwards (same sources). The Apple TV acknowledges none of these events ([pyatv #2325](https://github.com/postlund/pyatv/issues/2325)). Smoothness therefore depends on the phone sending frames at a steady pace and on Wi-Fi jitter, not on round trips. No measured latency figures exist for tvOS 26/27. pyatv has shipped touch since 0.15.0 in August 2024, and the research found no breakage reports ([pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). For scrubbing in the player, `_mcc` 7 skip or MRP seek is more predictable than emulated swipes.

### Keyboard and app launcher share the same Companion session

Text input runs over Companion's Remote Text Input (RTI) session. The client sends `_tiStart`, and the Apple TV then pushes `_tiStarted` when a text field gets focus and `_tiStopped` when it loses it, which is exactly the "keyboard appeared" signal an Android app needs to open its own keyboard; a field that was already focused when the app connected shows up as a `_tiD` payload in the `_tiStart` response ([pyatv companion/api.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/api.py)). Editing sends a `_tiC` event whose `_tiD` field is an NSKeyedArchiver-encoded RTI payload holding the session UUID and either an insert-text or a clear operation. To read the current text, pyatv restarts the session and takes `documentState.docSt.contextBeforeInput`, the text before the cursor, which is not guaranteed to be the whole field (same source). This is mature. pyatv has offered get, set, append and clear since 0.12.0 (May 2023), and a focus listener since 0.13.0 ([pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). Home Assistant uses it to type search queries ([HA apple_tv doc](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/apple_tv.markdown)). The dvdsgl and msthind04 Android apps both open their keyboard automatically, and msthind04 adds a direct-reply notification so text can be sent from the notification shade ([dvdsgl README](https://github.com/dvdsgl/tv-remote/blob/main/README.md); [msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)).

Two gaps remain. No source says whether password fields accept RTI input. And for one user, focus events stopped firing on tvOS 26.5 with pyatv 0.17.0; that issue has been open since May 2026 ([pyatv #2853](https://github.com/postlund/pyatv/issues/2853)). Apps that draw their own letter grid instead of using a system text field will probably never open an RTI session (inference), so D-pad typing stays as the fallback.

The launcher is just as feasible but needs defensive coding. `FetchLaunchableApplicationsEvent` returns a dictionary of bundle IDs to localized names, such as `com.netflix.Netflix: Netflix`, and `_launchApp` opens an app by `_bundleID` or follows a deep link given in `_urlS` ([pyatv protocols.md](https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md)); known-good links include tv.apple.com, disneyplus.com, play.hbomax.com and netflix.com/title URLs ([pyatv Apps doc](https://pyatv.dev/development/apps/)). Launching fails after an Apple TV reboot until the client has sent a `_sessionStart` to `com.apple.tvremoteservices` ([pyatv protocols.md](https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md)). **The device returns no icons.** The community workaround is Apple's public iTunes Lookup API queried by bundle ID, which misses built-in apps such as `com.apple.TVMusic` ([pyatv #1536](https://github.com/postlund/pyatv/issues/1536)) and, as msthind04 notes, tells Apple which apps the user has installed ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)).

Reliability was the real problem in 2026. On tvOS 26.5, `_launchApp` returned an `FBSOpenApplicationErrorDomain` error that pyatv silently ignored, and the issue was closed in October 2026 with no stated fix ([pyatv #2868](https://github.com/postlund/pyatv/issues/2868)). On the same build an Apple TV 4K (3rd generation) stopped answering the app-list request while a 2nd-generation box kept working ([pyatv #2845](https://github.com/postlund/pyatv/issues/2845)), and the tvOS 27.2 beta produced "apps is blocked" errors ([pyatv #2928](https://github.com/postlund/pyatv/issues/2928)). Neither protocol reports the app actually on screen; MRP's now-playing client is the closest substitute, and it is empty whenever nothing is playing ([pyatv metadata doc](https://pyatv.dev/development/metadata/)).

### Now playing needs the second pairing; volume depends on the living room

pyatv's metadata table is blunt: MRP supplies every now-playing field, while for "AirPlay and Companion: none" ([pyatv metadata doc](https://pyatv.dev/development/metadata/)). These MRP messages travel through the AirPlay tunnel ([pyatv mrp/player_state.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/mrp/player_state.py); [CommandInfo.proto](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/mrp/protobuf/CommandInfo.proto)):

| Message | Purpose |
|---|---|
| `SetStateMessage` | Playback state, supported commands, and the playback queue with each item's metadata |
| `SetNowPlayingClient`, `SetNowPlayingPlayer` | Identify the playing app |
| `PlaybackQueueRequest` | Fetch artwork at a requested size |
| `SendCommand` | Seek (45), repeat (46), shuffle (47) |

Field numbering is a trap: `PlayerPath.client` is field 2, elapsed time lives in `ContentItemMetadata.elapsedTime` (field 35) next to `duration` (field 14), and track metadata sits in `playbackQueue.contentItems` rather than `nowPlayingInfo` ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)). Data quality depends on each streaming app ([HA apple_tv doc](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/apple_tv.markdown)). Long-standing pyatv bugs, such as artwork not updating and position drifting, show the feature is never finished ([pyatv metadata issues](https://github.com/postlund/pyatv/issues?q=metadata)). On tvOS 27, a Rust port reports that pyatv's bundled `AudioRoute.proto` "silently drops now-playing metadata". No released pyatv version fixes this ([rust-atv](https://github.com/PapeThePope/rust-atv)).

**There may be a way to get now playing with one pairing.** Since the tvOS 18 era, Apple's own Remote subscribes over Companion to a `NowPlayingInfo` event and sends `FetchCurrentNowPlayingInfoEvent`. The reply is an NSKeyedArchiver `TVRCNowPlayingInfo` with the title, timing, artwork data and InSight metadata. A paginated `FetchUpNextInfoEvent` returns the Up Next list. Netflix fills in this data ([pyatv #2461](https://github.com/postlund/pyatv/issues/2461); [pyatv #2325](https://github.com/postlund/pyatv/issues/2325)). pyatv does not implement it, because the maintainer wants a stable, mapped API first ([pyatv #2461](https://github.com/postlund/pyatv/issues/2461)). Its schema is known only from captures posted in those issues. Even so, it could avoid the fragile AirPlay pairing entirely.

Volume depends more on the living-room setup than on the protocol ([HA apple_tv doc](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/apple_tv.markdown)):

| Audio setup | Relative volume (`_hidC` 8/9) | Absolute volume and readback |
|---|---|---|
| TV speakers controlled over HDMI-CEC | Works | No |
| Volume controlled by IR | Nothing works remotely | No |
| HomePod output | Works | Works ("all volume controls should work") |

Absolute set and readback use Companion `_mcc` 6 and 5, with `_vol` between 0 and 1, when the `_iMC` volume bit (0x100) is set. The alternative is MRP `SetVolume` per output device, which pyatv added in 0.17.0 ([companion/__init__.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/__init__.py); [pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). msthind04 shows a volume slider only when the Apple TV reports that it can route volume ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)).

There is no confirmed native mute. Users emulate it by setting volume to 0, but then cannot restore the previous level ([pyatv #2555](https://github.com/postlund/pyatv/issues/2555)). The "18 = mute" reading above is unverified.

### Power, profiles and extras are cheap but uneven

Sleep and wake are `_hidC` 12 and 13. The box reports its attention state through `FetchAttentionState` and through pushed `SystemStatus`/`TVSystemStatus` events: 1 asleep, 2 screensaver, 3 awake, 4 idle ([pyatv protocols.md](https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md); [companion/__init__.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/__init__.py)).

**Power state is the feature that broke most often.** tvOS 18.4 answered `FetchAttentionState` with "No request handler" ([pyatv #2648](https://github.com/postlund/pyatv/issues/2648)), tvOS 26.5 broke power control in Home Assistant until pyatv 0.18.0 added the `TVRCSessionStart` registration ([HA core #166545](https://github.com/home-assistant/core/issues/166545)), and the Apple TV pushes status events only to a client that sent a stable, non-null `_i` in `_systemInfo` ([companion/api.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/api.py)). The MRP alternative is worse: pyatv calls MRP power control "not very robust" because turning the box off works by navigating the Control Center UI ([pyatv Supported Features](https://pyatv.dev/documentation/supported_features/)), and that navigation stopped clicking the button on tvOS 18 ([pyatv #2502](https://github.com/postlund/pyatv/issues/2502)). Screensaver state matters in practice, because while the screensaver is on the first command only dismisses it ([pyatv #2648](https://github.com/postlund/pyatv/issues/2648)).

Deep sleep is the hard case. Apple TVs on Ethernet drop off the network in standby, and a Wake-on-LAN packet failed to wake one ([pyatv #2369](https://github.com/postlund/pyatv/issues/2369)); jrs8205's remote gives up on the network and wakes the box through the TV's HDMI-CEC link instead ([jrs8205/Apple-tv-remote](https://github.com/jrs8205/Apple-tv-remote)). On tvOS 27.0, Home Assistant's first attempt to wake a sleeping box fails while a retry 15 seconds later works, apparently because of a stale connection ([HA core #188039](https://github.com/home-assistant/core/issues/188039)). The sensible design is to rediscover through the sleep proxy, reconnect, send Wake, and retry once before reporting failure.

User profiles are the most stable advanced feature. `FetchUserAccountsEvent` returns `{account_id: name}`, and `SwitchUserAccountEvent {SwitchAccountID}` switches profile. Both have been in pyatv since 0.11.0 (May 2023), with no breakage reports in 2025 or 2026 ([companion/api.py](https://github.com/postlund/pyatv/blob/master/pyatv/protocols/companion/api.py); [pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). How profile switching interacts with tvOS 27's new per-profile app restrictions is untested ([MacRumors](https://www.macrumors.com/2026/09/14/apple-releases-tvos-27/)).

Most remaining extras are single messages: screensaver is `_hidC` 11, fast-forward and rewind are `_mcc` 8–11, and audio-output selection is MRP `ModifyOutputContextRequest`, in pyatv since 0.13.0 ([pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). AirPlay "send URL to TV" currently fails with HTTP 500 on tvOS 26.2+ ([pyatv #2906](https://github.com/postlund/pyatv/issues/2906)). Captions toggling via `_mcc` 12/13 "had no visible effect in Netflix, YouTube, or Zee", and Find My Siri Remote (`FetchSiriRemoteInfo`, `ToggleFindingMode`) was captured from Apple's Remote but is implemented nowhere in pyatv ([pyatv #2325](https://github.com/postlund/pyatv/issues/2325)).

### Siri voice is contested, and four features have no message at all

Siri voice is the one place where the evidence directly conflicts. pyatv's open investigation (last activity July 2026) found that voice travels as `_siriStart`, then `_siA` frames of narrowband audio (Opus/SILK, 8 kHz, 20 ms each), then `_siriStop`. Replaying a captured session opened the Siri UI, but the speech was never transcribed. Malformed data can soft-lock the Apple TV. The leading theories are that processing is gated on Siri capability data in `_systemInfo`, or on an Apple ID check ([pyatv #2875](https://github.com/postlund/pyatv/issues/2875)).

Two projects claim otherwise. The Rust project ratv lists "Siri voice input as Opus 16 kHz" among its features ([ratv](https://github.com/henrikwidlund/ratv)). dvdsgl's Android remote lists "Siri hold-to-talk" ([dvdsgl/tv-remote](https://github.com/dvdsgl/tv-remote)). The research could not confirm that either works end to end. The safe position is that voice is an experiment, not a planned feature.

Separately, the research found no message that returns app icons from the device, the app currently on screen, a restart, or a notification feed. The icon gap is a long-standing open pyatv issue ([pyatv #1536](https://github.com/postlund/pyatv/issues/1536)).

## tvOS 27 is the live target and the least-verified one

The protocols keep their shape, but the handshakes keep changing. Since 2021, several tvOS releases (major versions and mid-cycle x.4/x.5 updates) have added a small, unannounced requirement. Third-party clients learned each one from breakage reports, not from documentation.

| tvOS release | When | What broke for third-party clients | Fix / status |
|---|---|---|---|
| 15 | Sep 2021 | Standalone MRP service removed; users had to pair again for AirPlay | pyatv 0.9.0 tunnels MRP over AirPlay ([CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)) |
| 18.4 | Mar 2025 | Companion connections close instantly; `FetchAttentionState` returns "No request handler" | pyatv 0.16.1 (Jul 2025) sends a stable, non-null `_i` ([#2656](https://github.com/postlund/pyatv/issues/2656); [#2648](https://github.com/postlund/pyatv/issues/2648)) |
| 26.3 | 2026 | Companion pairing silently fails with no PIN on screen | Open ([#2837](https://github.com/postlund/pyatv/issues/2837)) |
| 26.4/26.5 | Mar–May 2026 | Power control and power state lost; a 4K gen 3 box stops answering requests; `_launchApp` error code 4 | `TVRCSessionStart` in pyatv 0.18.0 (Jun 2026), shipped in HA 2026.7 ([HA #166545](https://github.com/home-assistant/core/issues/166545)); launch issue closed without a stated fix ([#2868](https://github.com/postlund/pyatv/issues/2868)) |
| 26.5/26.6 | mid-2026 | AirPlay `/feedback` heartbeat falls out of sync and the link drops after ~35–40 s; `/pair-pin-start` times out | Open ([#2893](https://github.com/postlund/pyatv/issues/2893); [#2908](https://github.com/postlund/pyatv/issues/2908)) |
| 27 betas → 27.0 | Jun–Sep 2026 | AirPlay pairing shows no PIN; HTTP 470 after PIN entry | `X-Apple-Client-Name` header fix in an unmerged PR ([PR #2894](https://github.com/postlund/pyatv/pull/2894)); setting an AirPlay password is a reported workaround ([#2866](https://github.com/postlund/pyatv/issues/2866)) |
| 27.2 beta | Oct 2026 | Companion `connection_closed` every 0–10 s; "apps is blocked" | Open ([#2928](https://github.com/postlund/pyatv/issues/2928)) |

The pattern matters more than any single fix. A modern client must send a stable, non-null `_i` in `_systemInfo` (needed since 18.4), register `TVRCSessionStart {ProtocolVersionKey: "1.2"}` after `_sessionStart` (needed since 26.5), and send an `X-Apple-Client-Name` header on AirPlay `/pair-pin-start` and on every `/pair-setup` request (needed since 27). Without that header tvOS logs "passcodeString is empty or clientName is nil. Bailing." and never shows the PIN, because pyatv sends the client name only inside the encrypted M5 message, which arrives too late ([pyatv Protocols](https://pyatv.dev/documentation/protocols/); [PR #2894](https://github.com/postlund/pyatv/pull/2894)). Older devices simply return an error for `TVRCSessionStart`, so sending it every time is safe ([pyatv Protocols](https://pyatv.dev/documentation/protocols/)). Nobody has documented whether Companion pairing will also come to need the client-name header, and the HTTP 470 "Connection Authorization Required" error after PIN entry has no known root cause ([pyatv #2866](https://github.com/postlund/pyatv/issues/2866)). In one tvOS 27 beta even Apple's own iPhone Remote pairing code failed to appear ([HA core #173352](https://github.com/home-assistant/core/issues/173352)), a reminder that Apple changes these flows for its own reasons.

**The reference library is slowing down while tvOS keeps moving.** pyatv has shipped one or two releases a year since 2023 (0.16.1 in July 2025, 0.17.0 in January 2026, 0.18.0 on June 19, 2026), and 0.18.0 was still the latest on November 14, 2026, two months after tvOS 27 shipped ([PyPI pyatv](https://pypi.org/pypi/pyatv/json)). The maintainer's 0.18.0 notes read: "Due to my lack of free time, please feel free to send me PRs" ([pyatv CHANGES.md](https://github.com/postlund/pyatv/blob/master/CHANGES.md)). Home Assistant pins `pyatv==0.18.0` ([HA manifest](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/apple_tv/manifest.json)), as does the Unfolded Circle remote integration ([UC CHANGELOG](https://raw.githubusercontent.com/unfoldedcircle/integration-appletv/main/CHANGELOG.md)), so every pyatv regression reaches the whole ecosystem at once. Some tvOS 27 bugs are now found first in ports, such as the AudioRoute.proto metadata drop flagged by rust-atv ([rust-atv](https://github.com/PapeThePope/rust-atv)). Owning the code in Kotlin also removes one class of breakage: srptools 2.0.0 (October 2026) broke pyatv's pairing simply by changing its API ([pyatv #2934](https://github.com/postlund/pyatv/issues/2934)).

**The installed base is now split, and most "verified" claims predate tvOS 27.** tvOS 27 runs only on the Apple TV 4K 2nd and 3rd generations. The 1st-generation 4K and the Apple TV HD stay on tvOS 26.x ([MacRumors](https://www.macrumors.com/2026/09/14/apple-releases-tvos-27/); [Tom's Guide](https://www.tomsguide.com/tvs/not-every-apple-tv-4k-is-getting-tvos-27-heres-how-to-tell-if-your-box-is-eligible)). An Android remote must therefore serve both lines at once. That changes how to read the "verified" badges in project READMEs:

| Project | Hardware tested | tvOS |
|---|---|---|
| msthind04 ([repo](https://github.com/msthind04/AppleTV-Remote)) | Apple TV 4K 3rd gen (AppleTV14,1) | 26.6 |
| node-appletv-remote ([repo](https://github.com/energee/node-appletv-remote)) | AppleTV6,2 and AppleTV5,3 | 26.6 |
| ratv ([repo](https://github.com/henrikwidlund/ratv)) | AppleTV6,2 | 26.6.1 |
| rust-atv, upstream run ([repo](https://github.com/PapeThePope/rust-atv)) | Apple TV 4K 3rd gen | **27.0** (August 2026) |

AppleTV6,2 and AppleTV5,3 are the 1st-generation 4K and the HD, which cannot run tvOS 27. The rust-atv upstream run is the only live tvOS 27 verification in the research. **No Android implementation documents testing on tvOS 27.**

Behavior can also differ by model on the same build: on tvOS 26.5 a 4K gen 3 failed where a gen 2 worked ([pyatv #2845](https://github.com/postlund/pyatv/issues/2845)). New hardware is arriving that the libraries do not yet recognize. On November 14, 2026, Unfolded Circle had to add discovery for an "Apple TV 4K (4th generation)" ([UC CHANGELOG](https://raw.githubusercontent.com/unfoldedcircle/integration-appletv/main/CHANGELOG.md)), though whether that box has actually shipped is unconfirmed, and an "Apple HomeView (HomeAccessory17,1)" running software 27.2 never shows an AirPlay PIN ([pyatv #2951](https://github.com/postlund/pyatv/issues/2951)). dvdsgl's discovery code keeps only devices whose model name starts with `AppleTV` ([dvdsgl Discovery.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/Discovery.kt)). Such a filter would miss new models; filtering on the `rpFl` pairing bit is more future-proof (inference).

Two more cautions. **Several Companion clients connected to one Apple TV at the same time are linked to random disconnects** ([pyatv #2845](https://github.com/postlund/pyatv/issues/2845); [pyatv #2928](https://github.com/postlund/pyatv/issues/2928)). That matters in homes that also run Home Assistant, so the app should hold exactly one connection and release it cleanly. Community reports also need filtering. In the tvOS 27 pairing thread, one user credited "27.5" with a fix on August 10, 2026, which was before tvOS 27.0 existed ([pyatv #2866](https://github.com/postlund/pyatv/issues/2866)).

## Six Kotlin remotes from 2026 turn the build into an integration job

The 2026 wave of pyatv ports changed the build-versus-reuse question. **Several native Kotlin implementations of Companion Link now exist inside Android app repositories under permissive licenses. One of them also covers the AirPlay-tunneled MRP path.** None is published as a Maven library, so reuse means vendoring or forking. On 2026-11-14 the coordinator independently confirmed that six of these repositories exist: msthind04/AppleTV-Remote, dvdsgl/tv-remote, H2FE1/TVRemote, heNch1g/atv_remote_android, jrs8205/Apple-tv-remote and postlund/pyatv. Claims about the others rest on the researchers' reading of each project's README and source.

| Project | License | What it contains | Fit for this app |
|---|---|---|---|
| [msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote) | Apache-2.0 | Pure Kotlin/JVM `protocol/` module (OPACK, TLV8, HAP pairing, SRP, primitives, binary plist, Companion with RTI, AirPlay HAP channels, AP2 session, MRP codec), Compose app, desktop CLI, pyatv vectors | **Best base to vendor**; verified on tvOS 26.6, not 27 |
| [dvdsgl/tv-remote](https://github.com/dvdsgl/tv-remote) | MIT | Dependency-free Kotlin port of the Companion parts of pyatv 0.18; end-to-end test against pyatv's fake Apple TV | Reference for tests and minimal dependencies; no MRP |

**msthind04 is the most complete and the most carefully tested.** Its `protocol` module has no Android dependencies, and its crypto and serialization "are validated byte-for-byte against vectors generated from pyatv". The README lists real bugs those vectors caught: nonce truncation from Kotlin `Long` shift masking, loss of a leading zero byte in the SRP salt that breaks about **1 pairing in 256**, non-canonical binary plists that tvOS silently rejects, and unsigned OPACK integers ([msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote)). Each of these is the kind of bug that passes casual testing and fails in the field, which is the strongest argument for starting from this code rather than from scratch. The module needs Android 8.0, uses BouncyCastle and coroutines, and the release APK is about 3 MB (same source). Two other repositories have built on it already: puck is an explicit fork, and heNch1g has the same layout and file names ([iamclements/puck](https://github.com/iamclements/puck); [heNch1g/atv_remote_android](https://github.com/heNch1g/atv_remote_android)).

dvdsgl's port is smaller and Companion-only. It writes its own Curve25519 math with `BigInteger`, which its author admits is "slow next to native code… and not constant time" ([dvdsgl Curve25519.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/companion/Curve25519.kt)). That part is a reason not to copy it. Its test setup is worth copying: it uses pyatv to generate golden vectors and to run a fake Apple TV for end-to-end tests ([dvdsgl README](https://github.com/dvdsgl/tv-remote/blob/main/README.md)). It also proves that an open-source remote can be distributed through Google Play. The GitHub build is free, while the Play build sells dark mode as a $2.99 one-time upgrade (same source).

The Apache-2.0 and MIT code can go into a closed-source app with attribution. GPL-3.0 (jrs8205) and LGPL-3.0 (go-atv) code should be read, not copied, unless the app will be open source.

Outside the JVM, the ports matter mainly as cross-references. node-appletv-remote (MIT, 0.5.0 in October 2026) has the most honest status matrix, separating features marked "Verified" on real hardware from those covered only by loopback tests ([node-appletv-remote](https://github.com/energee/node-appletv-remote)). basmilius/apple-protocols (TypeScript, MIT) powers Homey; its README credits an AI coding assistant with handshake debugging and says automated tests are deferred ([apple-protocols](https://github.com/basmilius/apple-protocols)). go-atv (LGPL-3.0) explicitly skips touch, text input and media commands ([go-atv](https://github.com/jkiddo/go-atv)). ratv (MIT/Apache-2.0) is the most ambitious Rust option, and its protocol crates do no I/O ("take bytes and return bytes"), which would suit a JNI binding; but a crates.io lookup for `ratv` returned 404, so treat it as a GitHub-only project usable as a git dependency, and Android is not among its listed platforms ([ratv](https://github.com/henrikwidlund/ratv)). swift-atv and itsytv-core cover Apple platforms, where Apple's own Remote already exists ([swift-atv](https://github.com/jakejarvis/swift-atv); [itsytv-core](https://github.com/nickustinov/itsytv-core)), and HAP-Java implements the accessory (server) side of HomeKit rather than the controller side this app needs ([HAP-Java](https://github.com/hap-java/HAP-Java)).

Several 2026 repositories openly say they were built with LLM help. A status table backed by real hardware tests is the best signal of which ones to trust.

**The commercial competition is weak, and reliability is the open lane.** Rating and download figures below come from aggregators and APK mirrors, so treat them as low confidence.

| App | Ratings and downloads | Notes |
|---|---|---|
| Kraftwerk 9, "Remote for Apple TV" | 2.9★ and 500,000+ downloads on AppBrain ([AppBrain](https://www.appbrain.com/app/remote-for-apple-tv/com.kraftwerk9.appletv)); about 3.5★ from roughly 6,600 reviews on one mirror ([apkgk](https://apkgk.com/com.kraftwerk9.appletv)) | Reviews complain about lost volume controls, an app that "doesn't load at all", and ads pushing a 7-day trial ([Google Play](https://play.google.com/store/apps/details?id=com.kraftwerk9.appletv)) |
| CiderTV | 2.49★ ([AppBrain](https://www.appbrain.com/app/remote-for-apple-tv-cidertv/com.ezzi.cidertv)) | Still supports only Apple TV 2nd and 3rd generation boxes ([Amazon](https://www.amazon.com/Remote-for-Apple-TV-CiderTV/dp/B01BKQRZT6)) |

The recurring hard problems across every app are discovery across VLANs, stale connections and port rotation, waking from deep sleep, and the second pairing. Solving those well is the differentiator, not adding more features.

## Native Kotlin fits Android better than Python, Rust or KMP

### A pure-JVM protocol module is the proven architecture

**Embedding pyatv through Chaquopy is blocked in practice.** pyatv 0.18.0 requires `cryptography>=44.0.1`, `pydantic>=2` and `zeroconf>=0.129.0` ([PyPI pyatv](https://pypi.org/project/pyatv/)), and as of November 14, 2026 cryptography 50.0.2, pydantic-core and zeroconf publish no Android wheels ([PyPI cryptography](https://pypi.org/project/cryptography/); [PyPI zeroconf](https://pypi.org/project/zeroconf/)). Chaquopy 17 "will no longer install sdists from PyPI" ([Chaquopy changelog](https://github.com/chaquo/chaquopy/blob/master/product/runtime/docs/sphinx/changelog.rst)), and Chaquopy's own recipe directory stops at cryptography 42.0.8, below pyatv's floor, with no recipes for pydantic-core or zeroconf ([Chaquopy packages](https://github.com/chaquo/chaquopy/tree/master/server/pypi/packages)). Devices with 16 KB memory pages need Python 3.13+, each ABI adds "several MB" ([Chaquopy changelog](https://github.com/chaquo/chaquopy/blob/master/product/runtime/docs/sphinx/changelog.rst); [Chaquopy FAQ](https://github.com/chaquo/chaquopy/blob/master/product/runtime/docs/sphinx/faq.rst)), and apps targeting Android 17 must load only read-only native libraries ([Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17)). The research found no public example of an Android app shipping pyatv this way; the approach is plausible only as a prototype that requires custom-built wheels.

**A Rust core has a precedent only on the opposite side of the connection.** atv-core ships a tokio-and-JNI library that makes an Android TV *act as* an Apple TV for the iPhone Remote ([atv-core](https://github.com/corvofeng/atv-core/blob/main/README.md)), and no published Rust controller crate exists, so this route means writing the protocol in Rust and binding it, which only pays off if the same core must also ship on desktop or Wear. **Kotlin Multiplatform adds little** for an Android-only remote, though it costs little if the protocol module avoids `java.*` APIs, for example via cryptography-kotlin 0.6.0, which added Ed25519, X25519 and ChaCha20-Poly1305 on top of platform providers ([cryptography-kotlin 0.6.0](https://newreleases.io/project/github/whyoleg/cryptography-kotlin/release/0.6.0)). The architecture every working precedent uses is a pure Kotlin/JVM protocol module, an Android app module and a desktop CLI harness ([msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote); [gavinsan33/tvremote](https://github.com/gavinsan33/tvremote)), which lets the hardest code be unit-tested on the JVM without an emulator.

### Crypto: platform APIs where documented, a library for curves, hand-written SRP

Android's built-in crypto (JCA) documents these algorithms by API level:

| Algorithm | Available from | Source |
|---|---|---|
| ChaCha20-Poly1305 with a 96-bit nonce | API 28 | [Cipher](https://developer.android.com/reference/javax/crypto/Cipher) |
| X25519 key agreement (`XDH`) | API 33 | [KeyAgreement](https://developer.android.com/reference/javax/crypto/KeyAgreement) |
| `Ed25519` signatures | API 33 | [Signature](https://developer.android.com/reference/java/security/Signature) |

**Sources conflict on Ed25519 at API 33.** The current Signature reference lists Ed25519 at 33+. dvdsgl's code comment says Android 13's providers do not document importing raw 32-byte keys and that "Ed25519 signing isn't listed at all" ([dvdsgl Curve25519.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/companion/Curve25519.kt)). The table may have been updated after the author checked. Either way, raw-key import is undocumented, and HAP works entirely in raw 32-byte keys.

The practical answer avoids the question. Use BouncyCastle's lightweight API (`X25519PrivateKeyParameters`, `Ed25519Signer`, `HKDFBytesGenerator`), as three precedents do with bcprov 1.78–1.80; 1.87 is the newest release ([BouncyCastle Maven metadata](https://repo1.maven.org/maven2/org/bouncycastle/bcprov-jdk18on/maven-metadata.xml)). The alternative is Tink's `subtle` package (`X25519`, `Ed25519Sign`/`Ed25519Verify`, `Hkdf`), version 1.24.0 ([tink-java subtle](https://github.com/tink-crypto/tink-java/tree/main/src/main/java/com/google/crypto/tink/subtle)). Tink's ChaCha20-Poly1305 with a caller-supplied nonce lives in an *internal* package, so that piece should come from JCA or BouncyCastle (same source).

Using JCA for the cipher has two gotchas: Android names it `ChaCha20/Poly1305/NoPadding` rather than the JDK's `ChaCha20-Poly1305`, and the app needs a fresh `Cipher` per message because the JDK refuses to re-initialize one with the same key and nonce ([dvdsgl Crypto.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/companion/Crypto.kt)).

**Every Android precedent writes its own SRP-6a**, about 100 lines over `BigInteger`, because HAP's encoding differs from library defaults: the `k` and `u` operands are zero-padded to the 384-byte modulus, the proof integers use minimal-length encoding, and the salt is hashed exactly as the device sent it ([msthind04 Srp.kt](https://github.com/msthind04/AppleTV-Remote/blob/main/protocol/src/main/kotlin/dev/atvremote/protocol/crypto/Srp.kt)). A BouncyCastle issue reports that its SRP "is working only when BouncyCastle is being used on both sides" ([bc-csharp #506](https://www.github.com/bcgit/bc-csharp/issues/506)). That makes a hand-written client checked against pyatv vectors the lower-risk choice.

OPACK, TLV8 and binary plist are each a few hundred lines. Every Kotlin project writes its own, and the research found no JVM OPACK library ([dvdsgl Opack.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/companion/Opack.kt); [msthind04 Opack.kt](https://github.com/msthind04/AppleTV-Remote/blob/main/protocol/src/main/kotlin/dev/atvremote/protocol/opack/Opack.kt)).

For MRP, msthind04 deliberately uses a hand-written protobuf wire codec. Now playing touches "about six fields across four" messages, and reading the wire format directly "tolerates unknown fields from newer tvOS revisions" ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)). If the app later needs output devices or queue control, generating code with Square Wire or protobuf-javalite from pyatv's `.proto` files will scale better. A pending pyatv PR adds definitions reverse-engineered from Apple's libraries ([pyatv PR #2834](https://github.com/postlund/pyatv/pull/2834)).

### Discovery under Android 17's local-network permission

Use **NsdManager**, gated by SDK-extension version rather than plain API level ([NsdManager](https://developer.android.com/reference/android/net/nsd/NsdManager)):

| SDK extension | Covers | What changes |
|---|---|---|
| T-extension 22 | all Android 14+ devices | `registerServiceInfoCallback` combines discovery and resolution and pushes TXT, address and loss updates |
| T-extension 7 | foreground apps | No need to hold a `MulticastLock` |
| Older devices | — | Resolve one service at a time and hold the lock while discovering |

jmDNS and other raw-multicast libraries are worse on Android. They need the multicast lock, which "can cause a noticeable battery drain" ([WifiManager.MulticastLock](https://developer.android.com/reference/android/net/wifi/WifiManager.MulticastLock)).

**The big 2026 change is Android 17's `ACCESS_LOCAL_NETWORK`.** It is a runtime permission in the NEARBY_DEVICES group, and for apps targeting API 37 it gates *all* LAN traffic (outgoing TCP, UDP, multicast and `.local` name resolution) across every networking library; when it is denied, TCP connections typically just time out ([Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)). The alternative is a system picker (`DiscoveryRequest.FLAG_SHOW_PICKER`) that grants access to one user-chosen device without the permission, with `FLAG_USER_APPROVED_ONLY` rediscovering it later without UI (same source). None of this bites yet: Play has required target API 36 since August 31, 2026, and apps below API 37 receive an implicit grant from `INTERNET` ([Play target API](https://support.google.com/googleplay/android-developer/answer/11926878); [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)), so `INTERNET` plus `ACCESS_NETWORK_STATE` is all the app needs today. **One permission claim conflicts:** msthind04's README says it requests `NEARBY_WIFI_DEVICES` because that is "required for local service discovery on Android 13+", but the NsdManager reference lists no such requirement, and that permission's only documented role here was the now-deprecated Android 16 opt-in ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md); [NsdManager](https://developer.android.com/reference/android/net/nsd/NsdManager)).

The picker matters most for Tier 3. Android describes the picker grant in terms of one device's host addresses, and it is untested whether that covers the Apple TV's rotating Companion port *and* the dynamic AirPlay event and data ports, so a media-hub tier may need the full permission rather than the picker (inference).

### Connection lifetime, background work and credentials

The connection should live in an app-scoped repository and, while a session is active, be tied to a foreground service, because that service is "what keeps the process, and therefore the Companion and MRP connections, alive once the app leaves the screen" ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)). **The service type is a judgment call and a mild conflict between documentation and practice.** Android 14 requires a declared type for every foreground service, and Google describes `connectedDevice` as covering "interactions with external devices that require a… network connection" ([Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types)), which fits a remote, yet the precedents use `mediaPlayback` ([msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote); [heNch1g/atv_remote_android](https://github.com/heNch1g/atv_remote_android)). Since a remote plays no local audio, `connectedDevice` carries less Play-review risk (inference). Reconnection should start from scratch rather than from cache: rediscover over mDNS (because of port rotation), run pair-verify only, never pair-setup again, back off on failure, send periodic `NoOp` frames as keep-alives, and treat any failed write as a lost connection ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)).

**Credentials belong under a Keystore-held key.** `androidx.security:security-crypto` was deprecated in 2025 "in favour of existing platform APIs and direct use of Android Keystore" ([androidx.security releases](https://developer.android.com/jetpack/androidx/releases/security)). The current pattern, msthind04's, encrypts the Ed25519 seed and each device's key with an AES-GCM key held in Android Keystore, stores the blobs in DataStore or files, and excludes them from backup because Keystore-wrapped ciphertext "cannot be restored onto other hardware" ([msthind04 SecureStore.kt](https://github.com/msthind04/AppleTV-Remote/blob/main/app/src/main/kotlin/dev/atvremote/app/SecureStore.kt)). The Ed25519 identity cannot itself live inside Keystore, because pair-verify needs the raw key on every supported API level. dvdsgl keeps its keys in plain SharedPreferences, which is not a model to copy ([dvdsgl README](https://github.com/dvdsgl/tv-remote/blob/main/README.md)).

### Native touches users will notice

The integrations that make a remote feel native all have working precedents. Mapping the phone's hardware volume keys to the TV is trivial in the foreground with `onKeyDown` ([dvdsgl MainActivity.kt](https://github.com/dvdsgl/tv-remote/blob/main/android/app/src/main/java/xyz/dvdsgl/tvremote/MainActivity.kt)), and a platform `MediaSession` with `setPlaybackToRemote` turns the system volume panel into a TV slider whenever the Apple TV can route volume ([msthind04 NowPlayingService.kt](https://github.com/msthind04/AppleTV-Remote/blob/main/app/src/main/kotlin/dev/atvremote/app/NowPlayingService.kt)); the Media3 equivalent is `PLAYBACK_TYPE_REMOTE` ([Media3 DeviceInfo](https://developer.android.com/reference/androidx/media3/common/DeviceInfo)). The same MediaSession drives a lock-screen now-playing card with artwork and a scrubber for free ([msthind04 README](https://github.com/msthind04/AppleTV-Remote/blob/main/README.md)). Quick Settings tiles must use the `PendingIntent` overload of `startActivityAndCollapse`, because the `Intent` overload throws for apps targeting API 34+ ([Android 14 behavior changes](https://developer.android.com/about/versions/14/behavior-changes-14); [TileServiceCompat](https://developer.android.com/reference/kotlin/androidx/core/service/quicksettings/TileServiceCompat)). Glance 1.2.0 is stable for home-screen widgets ([Glance releases](https://developer.android.com/jetpack/androidx/releases/glance)), though Android 17 caps widget bitmap memory for apps targeting API 37 ([Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17)), and touchpad haptics through `HapticFeedbackConstants` are standard in the precedents ([dvdsgl/tv-remote](https://github.com/dvdsgl/tv-remote)).

The right SDK levels are **minSdk 26–28, compileSdk 37 and targetSdk 36**. minSdk 28 gets ChaCha20-Poly1305 from the platform with no extra code, while going up to dvdsgl's minSdk 33 buys little, because a curve library is still needed for raw keys and Android 8–12 users would be dropped.

## Four tiers, built in order of protocol risk

The tiers below follow protocol surface rather than UI ambition, because that is where the risk lives. Tier 1 uses only fire-and-forget Companion HID messages, which have not changed meaning since pyatv documented them. Tier 2 adds request/response and event-subscription features on the *same* Companion session and the same PIN, and those are exactly the calls that broke on tvOS 18.4, 26.5 and the 27.2 beta. Tier 3 adds a second protocol stack with its own PIN, which tvOS 27 currently disrupts, and Tier 4 collects undocumented or disputed messages.

|---|---|---|---|---|
| **1. | **2. Smart remote** | Touchpad with haptics; keyboard that opens on focus, plus a notification reply; app grid with cached iTunes icons and deep links; profile switcher; power-state indicator with an explicit "unknown"; Guide/Channel; Quick Settings tile | Adds `_touchStart`/`_hidT`; RTI `_tiStart`/`_tiC` with an NSKeyedArchiver (binary plist) codec; `FetchLaunchableApplicationsEvent`; `_launchApp` with error decoding; account events; `FetchAttentionState` plus `_interest` subscriptions | **1** (same Companion credential) | **Medium.** These are the calls that regressed on 18.4, 26.5 and 27.2 beta, and differ by model |

| **4. **The recommended approach is to start from msthind04's code rather than from a blank page.** Fork or vendor its Apache-2.0 `protocol/` module as the app's pure Kotlin/JVM protocol module, but treat pyatv master as the specification, not pyatv's prose docs and not any port. Then close the known gaps in the vendored code: all three HAP signature and proof checks, the tvOS 27 client-name header on AirPlay pairing, and decoding of `_em`/`_ec`/`_eu` error responses, which pyatv itself long ignored. Use dvdsgl's MIT code as an independent cross-check and copy its pyatv-driven golden-vector and fake-device testing, and build the UI in Jetpack Compose, as msthind04 does ([msthind04/AppleTV-Remote](https://github.com/msthind04/AppleTV-Remote)). The build order below front-loads the test harness because every bug msthind04 lists was a byte-level mismatch that only vectors catch.

| Phase | Build | Done when |
|---|---|---|
| 0. Harness | `:protocol` (pure JVM), `:app` and `:cli` modules. Generate golden vectors from pyatv master for OPACK, TLV8, SRP (including leading-zero salts), HKDF, nonces and binary plist. Run pyatv's fake Apple TV for end-to-end tests | Every codec matches pyatv byte-for-byte on the JVM |
| 1. Companion core | NsdManager plus manual IP. Pair-setup and pair-verify with full verification. Keystore-wrapped credentials keyed on a stable ID. Connect sequence: `_systemInfo` (stable `_i`) → `_touchStart` → `_sessionStart` → `TVRCSessionStart` → `_tiStart` → `_interest`. `NoOp` keep-alive, rediscover-then-reconnect, single-connection policy | Pairs once and survives port rotation, Wi-Fi changes and sleep on both a tvOS 26.x box and a tvOS 27.x Apple TV 4K gen 3 |
| 2. Tier 1 | Button pad, in-app volume keys, haptics, sleep/wake, Control Center (code 19, verified on hardware), multi-TV list | Usable as the household's daily remote with one PIN |
| 3. Tier 2 | Touchpad at 16 ms pacing with edge re-press; RTI keyboard plus notification reply; app grid with iTunes icons and an opt-out for the privacy leak; deep links; profiles; power indicator; Quick Settings tile | Every request/response feature fails visibly (retry or "unknown"), never silently |
| 4. Tier 3 | AirPlay pairing with client-name header and 470 handling; RTSP and HAP channels; heartbeat; MRP codec; MediaSession with remote volume; `connectedDevice` foreground service | Now playing stays live for an hour on tvOS 27 without the 35–40 s heartbeat desync |
| 5. Labs and platform | Spike on Companion `NowPlayingInfo` as a single-pairing alternative; Find My Remote; `_hidC` 18; captions. Android 17 migration to targetSdk 37 (`ACCESS_LOCAL_NETWORK` flow, picker testing across all Apple TV ports); Glance widget | Features ship behind flags; permission flow verified on Android 17 devices |

**Watch for regressions continuously.** Keep a test Apple TV on the tvOS beta channel. The early-warning feeds are pyatv's issue tracker and the Home Assistant and Unfolded Circle changelogs; the latter's "reconnect when Apple TV buttons stop responding" and "retry app discovery when Companion is unavailable" entries are exactly the failures an Android remote will hit ([UC CHANGELOG](https://raw.githubusercontent.com/unfoldedcircle/integration-appletv/main/CHANGELOG.md)). Plan for a fix release within weeks of each major tvOS release and each x.4/x.5 point release, without waiting for pyatv.

## Conclusion

The hard part of this app is not implementing it but keeping it working. The protocol work that took pyatv years is now available as permissively licensed Kotlin. What no one supplies is fast compatibility with tvOS releases: pyatv takes months to respond, and no Android project has documented tvOS 27 testing. A new entrant can therefore beat both the 2.5–3.5★ Play incumbents and the 2026 open-source wave on one thing, staying reliable across tvOS updates. Engineer for that from the first commit: hardware in the test loop on both tvOS 26 and 27, visible failure states instead of silent ones, and a release process that can ship a handshake fix within days.

The most promising strategic move is a spike on Companion's own `NowPlayingInfo` channel. Today the second AirPlay pairing is both the worst onboarding step (a second PIN) and the most fragile code path on tvOS 27. Apple's own Remote already receives title, timing and artwork over Companion, so if that archive can be decoded reliably, a one-PIN app that still shows now playing would be simpler and sturdier than any current competitor. Android 17's local-network permission sets the other deadline. Moving to targetSdk 37 forces the app to choose between a broad permission prompt and a per-device picker grant whose coverage of the Apple TV's dynamic ports is unproven. That test belongs early in the roadmap, not at the next Play target-API deadline.
